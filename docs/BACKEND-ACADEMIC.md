# Учебная логика: передача backend команде

В этой части подготовлены серверные правила и API для расписания, учебных
назначений и СРСП. Код ещё не развёрнут на рабочем сайте; миграция рабочей
базы PostgreSQL не запускалась. Распределение студентов, новые названия групп
и заполнение учебных планов в эту часть не входят.

## Что реализовано

- Фиксированные пары `p1`–`p12`, UTC+5, по 50 минут; после третьей, шестой и девятой пары
  перерыв 15 минут. Источник правил — `lib/studyhub/lesson-rules.mjs`.
- Не более трёх предметов у преподавателя, проверка языка преподавания,
  учебного плана группы по семестру и назначения преподавателя группе.
- СРСП связана с практикой той же группы и предмета; дата берётся из практики,
  отдельные время, аудитория и посещаемость отсутствуют.
- Проверка вместимости и пересечений при сохранении занятия; отдельный запрос
  доступности аудиторий для будущей формы выбора.
- Новые задания требуют `lessonId`; тип выводится из занятия. Существующие
  задания без этой связи остаются читаемыми и доступными для сдачи.
- Минимальная совместимость текущего интерфейса: отображение СРСП без времени
  и аудитории, фиксированные пары для обычного занятия, выбор занятия при
  публикации задания. Полная форма создания СРСП и новые фильтры ещё нужны.

API, тела запросов и ошибки описаны в [API.md](API.md), TypeScript-типы —
в `lib/studyhub/api-contract.ts`. Основные реализации находятся в
`academic-store.mjs`, `auth-store.mjs`, `learning-store.mjs` и `auth-http.ts`
каталога `lib/studyhub/`.

## Подготовка базы

Сетка заканчивается в 19:25. Для уже обновлённой PostgreSQL-базы нужна отдельная
миграция `database/migrations/evening-slots.mjs` с отметкой `evening_slots_v1`.
Она расширяет допустимые слоты и обновляет проверки времени для учебных занятий,
не меняя существующие записи. Сначала проверьте её на копии базы, затем выполните
с прямым подключением из приватного env-файла:

```powershell
node --env-file=<приватный-файл> scripts/migrate-evening-slots.mjs --host <проверенный-прямой-хост> --apply
```

Подключение задаётся в `DATABASE_URL_UNPOOLED` или `DIRECT_DATABASE_URL`.
В локальной SQLite-базе эта миграция выполняется при открытии после базовой
миграции учебных правил; повторный запуск ничего не меняет.

Минимальная миграция `database/migrations/academic-rules.mjs` добавляет поля
групп и аудиторий, связи преподавателей и учебных планов, `practice_id`,
`slot_id` и `school_assignments.lesson_id`. Старые записи сохраняются;
новые поля и ссылки могут оставаться `null`. Миграция не назначает предметы
преподавателям и не заполняет учебные планы по догадке.

Для локального SQLite миграция вызывается при открытии базы приложением.
Для существующего PostgreSQL её нужно выполнить явно **до запуска нового кода**,
сначала на отдельной тестовой базе или ветке Neon. Скрипт ожидает уже существующую
схему StudyHUB, проверяет прямой хост подключения и применяет изменения
в транзакции. Повторный запуск с установленной отметкой `academic_rules_v1`
не изменяет данные.

В локальном `.env.academic-qa.local` задайте `DATABASE_URL_UNPOOLED` тестовой
базы. Файл `.env*` исключён из Git. Затем из корня проекта:

```powershell
node --env-file=.env.academic-qa.local scripts/migrate-academic.mjs --host <проверенный-прямой-хост> --apply
```

Вместо `<проверенный-прямой-хост>` нужен только hostname из прямого подключения,
без логина, пароля или пути. Адрес с `-pooler` отклоняется. Команда меняет схему
указанной базы; не подставляйте сюда рабочее подключение для пробного запуска.

## Что должен заполнить участник, отвечающий за данные

Для новых групп без расписания язык можно указать при создании. Для существующих
групп, в том числе с `language: null`, сначала настройте языки всех преподавателей
их действующих и будущих занятий: иначе изменение языка группы будет отклонено.

1. Через `PUT /api/academic/teacher-languages` заполнить языки преподавателей,
   затем через `PUT /api/academic/teacher-subjects` — специализации.
2. У групп задать `program` (`IS`, `VTIPO`, `DS`), `intakeYear`, `language`
   (`kk` или `ru`), названия и состав. При заданном годе поступления курс
   вычисляется относительно текущего учебного года.
3. У аудиторий задать `number`, `floor`, `type` и вместимость. Типы:
   `computer`, `lecture`, `laboratory`, `ordinary`.
4. Через `PUT /api/academic/group-subjects` заполнить планы групп по учебному
   году и семестру. Например, ноябрь 2026 — `2026/1`, февраль 2027 — `2026/2`.
5. Создать назначения `teacherId + groupId + subjectId` через
   `PUT /api/teaching-assignments`, передавая дату нужного семестра.
6. После этого создавать занятия, СРСП и связанные задания.

При заполнении специализаций сохраните все предметы действующих и будущих
неотменённых занятий преподавателя, соблюдая предел в три предмета. Если старое
расписание этому не соответствует, участник, отвечающий за данные, должен явно
перепланировать или отменить несовместимые занятия при переносе данных.
Миграция не делает это автоматически и не сбрасывает расписание.

Три запроса `/api/academic/*` **заменяют весь список в выбранной области**,
а не добавляют отдельные элементы. Пустой массив очищает список; удаление
связи, используемой действующим или будущим неотменённым занятием, запрещено.
Поля `version` у этих запросов нет: параллельные записи выполняются последовательно,
и последний допустимый запрос заменяет предыдущий список. Перед редактированием
нужно заново загрузить полный список из `bootstrap`.
Число 3–4 преподавателя на один предмет — правило наполнения учебного набора,
его нужно обеспечить при распределении данных. Сервер ограничивает число
предметов у одного преподавателя тремя, но не требует сразу создать всех
преподавателей предмета одним запросом.

До заполнения этих связей старые данные можно просматривать. Создание или
существенное изменение занятия, его восстановление и новая публикация задания
могут вернуть ошибку настройки учебного плана. Отмена старого занятия или правка
его примечания доступны без переустройства исторического расписания.

## Что подключить участникам интерфейса

Использовать `teacherSubjects`, `teacherLanguages`, `groupSubjects` из
`bootstrap` для зависимых списков. Для аудитории запрашивать
`GET /api/rooms/availability` с `date`, `slotId`, `groupId`; при редактировании
администратором — также `excludeLessonId`. Проверять и `available`,
и `capacityOk`, а после сохранения обрабатывать серверные ошибки: предварительная
проверка не резервирует аудиторию.

В форме СРСП выбирать практику, блокировать собственные дату, время и аудиторию.
Отправлять `practiceId`, а поля `roomId`, `slotId`, `startsAt`, `endsAt`
не передавать либо передавать как `null`. Показывать `Lesson.date` и не пытаться
форматировать отсутствующее время. СРСП не должна создавать отдельную колонку
посещаемости или оценок журнала.

При отмене практики СРСП отображается отменённой. Уже выданное задание,
его срок и возможность сдачи сохраняются намеренно: отмена занятия не удаляет
учебную работу. Перенос практики меняет дату СРСП, но не срок сдачи задания.

При объединении с коммитом `8dd9a97` сохранены фильтры и хранение настроек
и черновиков проверки в `localStorage` из frontend-части. Они совместимы
с обязательным `lessonId` и отображением СРСП без собственного времени.
Расширенные формы, переименование групп и полный новый набор данных остаются
частями других участников. Подробнее: [фильтры и сохранение в браузере](ACADEMIC_FRONTEND.md).
