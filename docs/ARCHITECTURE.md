# Как устроен StudyHUB

## Один запрос от страницы до базы

```text
Страница app/tasks/page.tsx
  → компонент TasksPage
  → fetch('/api/assignments/.../submission')
  → обработчик app/api/.../route.ts
  → проверка сессии, роли и данных
  → SQL-запрос в SQLite
  → ответ JSON
  → обновление данных на странице
```

Next.js отвечает и за страницы, и за API. Отдельный Express-сервер не нужен.
Страницы и корневой layout — серверные компоненты. Формы, диалоги и кнопки
состояния написаны как клиентские React-компоненты с `'use client'`.

Каждый файл `app/.../page.tsx` подключает свой компонент. Общая оболочка
`studyhub-app.tsx` рисует меню и шапку, а содержимое получает через `children`.
Она больше не импортирует все кабинеты сразу. Переходы используют `next/link`.

## Где что изменять

- Новый экран: маршрут в `app/` и компонент в `components/studyhub/`.
- Новое поле или тип ответа: `lib/studyhub/api-contract.ts`.
- Проверка прав и значений: `lib/studyhub/policy.mjs`.
- HTTP-запросы и сообщения об ошибках: `lib/studyhub/auth-http.ts`.
- Аккаунты, справочники, расписание: `lib/studyhub/auth-store.mjs`.
- Задания, работы, оценки, материалы: `lib/studyhub/learning-store.mjs`.
- Таблицы и индексы: `database/schema.mjs`.
- Учебные примеры: `database/seeds/`, затем команда заполнения.
- Цвета: `app/styles/tokens.css`; общие правила: `app/styles/styles.css`.

## Авторизация и роли

Пароль хранится как scrypt-хеш. После входа сервер создаёт сессию в БД,
а браузер получает случайный идентификатор в HttpOnly-cookie.
У каждого запроса проверяется текущий пользователь. Студент получает
свои работы и оценки, преподаватель — только назначенные ему группы и предметы.

Изменения дополнительно требуют правильный Origin и CSRF-токен.
Поле `version` защищает от случайного перезаписывания записи, которую уже
изменил другой пользователь: сервер возвращает 409, и список нужно обновить.

Демонстрационные кнопки вызывают `POST /api/auth/demo`. Сервер входит в один
из трёх подготовленных аккаунтов; роль произвольного пользователя не меняется.
Этот API выключен в обычном режиме и не запускается на базе обычных аккаунтов.

## Данные

SQLite — отдельный файл базы на серверной стороне. В нём находятся таблицы
пользователей, групп, предметов, занятий, заданий, работ, оценок, посещаемости,
материалов и объявлений. Загруженные файлы тоже сохраняются в БД.
Исходники содержат только схему и код заполнения вымышленными примерами.
Браузер не импортирует примеры и не хранит учебные данные в localStorage.

Используются внешние ключи, индексы и транзакции. Режим WAL позволяет чтению
не блокировать запись обычным способом. Результаты запросов учебных данных
ограничиваются текущей ролью до отправки в браузер.

## Что изменено для скорости

- Кабинеты подключаются своими маршрутами, а не одним общим импортом.
- Провайдер черновиков преподавателя отделён от тяжёлого файла его страниц.
- После изменения запрашивается только `/api/bootstrap`, без повторного запроса сессии.
- Форматтеры дат создаются один раз и повторно используются в таблицах.
- Удалены неиспользуемые Tailwind и его CSS-загрузчик.
- Добавлены состояние загрузки, страница ошибки и понятная 404.

Это изменения в устройстве приложения; точное ускорение в процентах не измерялось.
Для защиты проекта полезно пройти путь одного запроса и объяснить, зачем
нужны серверная проверка роли и отдельная база.
