# Подключение к PostgreSQL

StudyHUB запускается на локальном сервере Next.js с Node.js 24. Здесь описано
подключение к PostgreSQL, импорт существующей базы и запуск готовой сборки.
Разделы 1–4 описывают Neon. Для нового тестового проекта Supabase ниже приведён
отдельный порядок подготовки.

## 1. Подключение базы

Для подключения к существующей учебной базе скопируйте приватную pooled-строку
подключения Neon с SSL. Если нужно перенести данные из SQLite, сначала создайте
пустую базу PostgreSQL. Скопируйте `.env.example` в `.env.local` и заполните настройки:

| Переменная           | Значение                                                               |
| -------------------- | ---------------------------------------------------------------------- |
| `DATABASE_URL`       | Приватная pooled-строка подключения Neon.                              |
| `STUDYHUB_DEMO_MODE` | `true` для учебной базы с выбором роли, `false` для обычных аккаунтов. |
| `STUDYHUB_ORIGIN`    | Адрес локального сайта без пути, например `http://localhost:3000`.     |

Строку подключения храните в `.env.local`. Для SQL-миграций сохраните прямую
строку подключения в отдельном приватном env-файле.

## 2. Перенос существующих данных

Остановите запись в исходную SQLite-базу и сохраните её резервную копию.
В целевую PostgreSQL-базу не должны успеть попасть аккаунты, сессии или другие записи:
сначала выполните импорт, затем открывайте сайт.

Из папки проекта, с Node.js 24.x и настроенным `.env.local`:

```powershell
npm ci
npm run db:import -- --source "C:\путь\к\auth.sqlite"
```

`--source` принимает абсолютный путь к существующему файлу SQLite. Команда
проверяет целостность базы, создаёт схему PostgreSQL и переносит записи в транзакции.
Исходный файл открывается только для чтения. После переноса сравниваются количества
записей и контрольные суммы содержимого таблиц.

Сохраняются идентификаторы, пользователи, связи, расписание, задания, оценки,
посещаемость, материалы и объявления. Хеши паролей **scrypt** переносятся без замены:
прежние пароли продолжают действовать. Двоичные файлы из SQLite `BLOB`
сохраняются в PostgreSQL `bytea`.

Сессии и временные ограничения входа (`auth_sessions`, `auth_limits`) не переносятся.
После перехода нужно войти заново. Повторный запуск допускается только для того же
снимка при неизменённых данных назначения; другой снимок или непустая база без
точного маркера отклоняются. Это однократный перенос, а не синхронизация.

Команды `demo:setup` и `demo:seed` готовят только локальную SQLite-базу.
Не запускайте их для заполнения Neon: `demo:seed` отклоняет непустой `DATABASE_URL`.

Старую SQLite-базу со шкалой 2–5 сначала обновите **в отдельной рабочей копии**.
Импортёр отклонит её до подключения к PostgreSQL, если у оценок ещё нет `status`.
Порядок подготовки копии приведён в [описании базы](../database/README.md#где-лежат-данные).

## 3. Обновление существующей PostgreSQL-базы до шкалы 0–100

Для уже заполненной Neon-базы нужен `scripts/migrate-grading.mjs`.
Запуск сайта сам по себе не выполняет PostgreSQL-миграцию. Новый интерфейс
журнала публикуется после обновления схемы.

Миграция переводит прежние оценки занятий и проверенных работ:
**2 → 40, 3 → 60, 4 → 80, 5 → 100**. Версии изменённых записей повышаются.
Прежние `absent` и `excused` становятся **Н** только при отсутствии числовой
оценки. **н.п.** означает «оценка не предусмотрена» и задаётся преподавателем
явно; это не обозначение уважительного пропуска. История посещаемости,
сданные работы, комментарии и файлы сохраняются.

Выполняйте обновление в таком порядке:

1. Сохраните резервную копию или отдельную ветку Neon для восстановления.
   Создайте от текущей Production-базы **отдельную QA-ветку**.
2. В приватный `.env.journal-qa` запишите прямую строку QA-ветки в
   `DATABASE_URL_UNPOOLED`. Она должна вести на хост без `-pooler`.
   Не вставляйте строку подключения или пароль в команду, документацию или Git.
3. Сверьте хост с выбранной QA-веткой в панели Neon и выполните команду ниже.
   Вместо текста в угловых скобках укажите только проверенное имя хоста.

```powershell
node --env-file=.env.journal-qa scripts/migrate-grading.mjs --host "<прямой хост QA>" --apply
```

Скрипт требует одновременно `--host` и `--apply`, проверяет точное совпадение
хоста и отклоняет pooled-подключение. Приоритет переменных подключения:
`DATABASE_URL_UNPOOLED`, затем `DIRECT_DATABASE_URL`, затем `DATABASE_URL`;
даже последнее значение должно быть прямым. Env-файл не заменяет уже заданную
одноимённую переменную терминала, поэтому используйте отдельное окно с нужными настройками.

4. Запустите новую сборку на QA-базе. Проверьте сохранность прежней работы,
   файла и комментария, преобразование оценок, новые значения 0 и 100,
   отметки Н/н.п., очистку и повторное открытие страницы. Для полного API-прогона
   запишите **pooled**-подключение этой QA-ветки в `.env.qa` и выполните
   `npm run test:postgres`; сначала нужна `npm run build`.
   Повторный вызов миграции должен сообщить, что шкала уже установлена,
   и не менять значения или версии.
5. После успешной QA-проверки приостановите запись через прежнюю версию сайта.
   Подготовьте отдельный приватный `.env.journal-production` с прямым Production URL,
   ещё раз проверьте резервную копию и хост. Выполните миграцию Production:

```powershell
node --env-file=.env.journal-production scripts/migrate-grading.mjs --host "<прямой хост Production>" --apply
```

6. Запустите новую версию по следующему разделу и проверьте вход и журнал.

Изменения схемы, данных и маркер `grading_scale_v2` записываются в одной
транзакции. При ошибке операция откатывается. Маркер и проверка схемы защищают
от повторного умножения оценок, в том числе новых баллов 2–5 по стобалльной шкале.
Для отката релиза восстановите согласованную резервную копию базы вместе
с прежней версией приложения; не удаляйте маркер и не делите оценки вручную.

SQLite обновляется автоматически при подключении новой версией приложения.
Перед первым запуском на старых локальных данных также сохраните резервную копию.

### Семестровые оценки и экзамен

Для существующей базы PostgreSQL перед запуском версии с семестровыми оценками
запустите миграцию `school_period_marks`. Она создаёт таблицу или добавляет оценку
за экзамен в существующую таблицу семестровых оценок. Укажите прямое подключение в
`DATABASE_URL_UNPOOLED` или `DIRECT_DATABASE_URL` и подставьте имя хоста выбранной базы.
Например, для QA-ветки выполните команду ниже.

```powershell
node --env-file=.env.journal-qa scripts/migrate-period-marks.mjs --host "<прямой хост QA>" --apply
```

Таблица хранит рубежные оценки, рейтинги и экзамен за каждый семестр. Команду можно
запускать повторно. При локальной работе с SQLite схема обновляется автоматически.

## 4. Локальный запуск с Neon

В `.env.local` укажите `DATABASE_URL` вашей базы и адрес локального сайта:

```dotenv
STUDYHUB_DEMO_MODE=true
STUDYHUB_ORIGIN=http://localhost:3000
```

```bash
npm run build
npm start
```

`npm start` запускает `next start`, который читает `.env.local`. Открывайте именно
[localhost:3000](http://localhost:3000); для `127.0.0.1` измените Origin соответственно.
Локальный сервер сохраняет изменения в Neon. Если данные перенесены из SQLite,
исходный файл остаётся отдельной резервной копией.

Для изолированных локальных тестов `npm test` явно задаёт пустой `DATABASE_URL`
и временный каталог SQLite. До тестов нужна готовая сборка. Обычный локальный
SQLite-режим также остаётся доступен при пустом `DATABASE_URL`.

Проверка PostgreSQL запускается через `npm run test:postgres` на свежей отдельной
QA-ветке Neon. Её строка подключения хранится в приватном `.env.qa`; адрес базы
должен отличаться от `.env.local`. Проверка меняет данные, поэтому для повторного
запуска QA-ветку нужно заново создать или сбросить.

## Файлы и ограничения

Новые работы и материалы ограничены **3 МиБ** (3 × 1024 × 1024 байт).
Файлы хранятся в приватной PostgreSQL-базе и выдаются только через API с проверкой прав.
Их объём учитывается в хранилище Neon; отдельная загрузка на публичный диск не используется.

## Supabase как PostgreSQL

StudyHUB подключается к базе через серверный драйвер `pg`. Вход, сессии и проверку
ролей выполняет существующий API Next.js. Файлы хранятся в PostgreSQL `bytea`.
Supabase Auth, Storage и клиентская библиотека для этого варианта не требуются.

### Подготовка проекта и URI

1. Создайте отдельный тестовый проект Supabase и сохраните пароль базы.
   До первоначального импорта откройте **Integrations → Data API** и выключите
   **Enable Data API**. Схема StudyHUB рассчитана на доступ через сервер приложения.
   Порядок отключения приведён в [документации Supabase](https://supabase.com/docs/guides/api/securing-your-api#disable-the-data-api).
2. Откройте **Connect** и скопируйте PostgreSQL URI. Для импорта используйте
   **Direct connection** или **Session pooler**. Direct обычно требует IPv6,
   а Session pooler доступен по IPv4 на порту `5432`. Для локального сервера
   подходит тот же выбор. Для serverless-развёртывания используйте
   **Transaction pooler** на порту `6543`. Хост и имя пользователя копируйте
   целиком из Connect. [Варианты подключения Supabase](https://supabase.com/docs/guides/database/connecting-to-postgres)
3. Подставьте пароль базы в URI, закодировав его зарезервированные символы
   в формате percent-encoding. Например, `@` становится `%40`, а `#` — `%23`.
   Кодируется значение пароля, вся строка URI сохраняет свою структуру.
   [Пароли в строке подключения](https://supabase.com/docs/guides/database/postgres/roles#special-symbols-in-passwords)
4. Используйте `sslmode=verify-full` для шифрования и проверки сервера.
   Команда импорта добавляет этот режим при отсутствии параметра, а значение
   `require` приводит к `verify-full`. В URI импорта допускаются только параметры
   `sslmode` и `sslrootcert`.
   Если Node.js не доверяет сертификату прямого подключения или Session pooler,
   скачайте корневой сертификат Supabase из
   **Database Settings → SSL Configuration**, сохраните вне репозитория и укажите
   абсолютный путь в `sslrootcert` URI с кодированием специальных символов пути.
   Проверку TLS оставьте включённой.
   [Настройка SSL и сертификата](https://supabase.com/docs/guides/platform/ssl-enforcement)

Создайте `.env.supabase.local` в корне проекта и запишите единственную настройку,
заменив текст в угловых скобках полной строкой подключения:

```dotenv
DATABASE_URL="<PostgreSQL URI из Connect с паролем и SSL>"
```

Этот файл исключён из Git. Он используется командой импорта.
Для запуска Next.js настройки задаются отдельно в `.env.local` или на хостинге.
Строка подключения и пароль должны оставаться на сервере, без префикса
`NEXT_PUBLIC_` и без помещения в браузерный код.

### Первоначальный импорт

В новом проекте таблицы StudyHUB должны быть пустыми. С Node.js 24.x выполните
из папки репозитория:

```powershell
npm ci
npm run db:supabase:import
```

Команда создаёт отдельный синтетический SQLite-набор в
`../studyhub-data/supabase-demo/auth.sqlite`. Первоначальная подготовка выполняется
во временной соседней папке. Готовый снимок используется повторно при повторах
команды. Рабочий SQLite-каталог из `STUDYHUB_DATA_DIR` остаётся отдельным источником.

Для переноса конкретной резервной копии с разрешёнными к загрузке данными укажите
её абсолютный путь:

```powershell
npm run db:supabase:import -- --source "C:\путь\к\auth.sqlite"
```

Импортёр открывает источник для чтения, проверяет целостность и связи, переносит
данные в транзакции и сверяет количества записей и контрольные суммы таблиц,
включая файлы. Дождитесь успешного завершения и отчёта импортёра. Повторный импорт
принимается только для того же снимка и неизменённой цели. Подготовка старой SQLite
и общие ограничения описаны в разделе 2 выше.

Если команда сообщает «Для импорта выберите Supabase direct или session pooler
на порту 5432», скопируйте соответствующий URI из Connect. Сообщение
«Для импорта нужен SSL с проверкой сервера» требует `sslmode=verify-full`.
При ошибке «Включите проверку TLS» уберите отключение проверки из окружения
терминала и используйте доверенный корневой сертификат. При общей ошибке
подключения проверьте пароль, режим Connect, сеть и сертификат.

### Локальная проверка и подключение сервера

После успешного импорта скопируйте подходящий URI с `sslmode=verify-full`
и при необходимости `sslrootcert` в `DATABASE_URL` файла `.env.local` и задайте:

```dotenv
STUDYHUB_DEMO_MODE=true
STUDYHUB_ORIGIN=http://localhost:3000
```

```bash
npm run build
npm start
```

На [localhost:3000](http://localhost:3000) проверьте вход студентом,
преподавателем и администратором через «Учебный доступ». У студента откройте
предметы и задания, у преподавателя сохраните тестовую отметку в журнале,
у администратора откройте группы и расписание. Обновите страницу и войдите снова,
чтобы проверить сохранение записи в целевой базе. Это план проверки подключённого
проекта, фактические результаты записываются отдельно после выполнения.

Для размещённого сервера задайте `DATABASE_URL` с подходящим pooler URI,
`STUDYHUB_ORIGIN` с точным HTTPS-адресом сайта и `STUDYHUB_DEMO_MODE` в настройках
хостинга. Значение `true` подходит для синтетического учебного набора,
`false` — для базы обычных аккаунтов. После изменения настроек перезапустите
или заново разверните сервер. Настройка `.env.supabase.local` сама по себе
не переключает работающий сайт на другую базу.
