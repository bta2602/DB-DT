# Скрытие занятий без потери учебных данных

Эта часть готовит базу для скрытия занятий. Обработчики API и элементы интерфейса
добавляются следующими участниками; до их установки вручную скрывать занятия
в рабочей базе нельзя: прежний API ещё учитывает их в расписании и занятости.

У занятия появился необязательный столбец `school_lessons.archived_at` (текстовая
дата UTC). `NULL` означает, что занятие видно в расписании. При скрытии следующий
backend должен записывать время операции и повышать `version`. Статус
`scheduled`/`cancelled` сохраняется: отмена и скрытие — разные действия.

Занятие физически не удаляется. Задания, отправленные работы, файлы, оценки и
посещаемость сохраняют свои внешние ключи. Они доступны в журнале и проверке
работ. Backend должен скрывать практику вместе с привязанными СРСП, одной транзакцией.
Исторические записи не превращаются в новые или самостоятельные занятия.
Скрытые занятия больше не занимают время группы, преподавателя и аудитории.
Создать новое задание или СРСП со ссылкой на скрытое занятие нельзя.

## Что делает миграция

Файл `database/migrations/lesson-archive.mjs` добавляет nullable-столбец и два
частичных индекса. Если включены академические ограничения, обновляются только
четыре связанных триггера; пользовательские триггеры и индексы сохраняются.
Строки учебных таблиц не переписываются и не удаляются. Повторный запуск проверяет
маркер `lesson_archive_v1` и не дублирует изменения.

SQLite применяет структурное обновление при открытии базы текущим приложением.
Для PostgreSQL обновление запускается отдельно, **до публикации нового backend**.
Приложение не меняет схему Neon автоматически.

## Проверка кода на компьютере

Из корня проекта после `npm ci`:

```powershell
node --test tests/lesson-archive-migration.test.mjs tests/academic-data-migration.test.mjs tests/academic-migration.test.mjs tests/evening-slots.test.mjs tests/academic-import.test.mjs
```

Тесты используют SQLite в памяти и записывающий адаптер для PostgreSQL. Они не
подключаются к Neon. Проверка с адаптером проверяет порядок SQL, транзакцию и
откат, но не заменяет запуск миграции на настоящей QA-ветке PostgreSQL.

При проверке 17 ноября 2026 года сборщик предупредил об известной уязвимости
закреплённой версии Next.js 16.4.2. Первый запуск остановился с
`SecurityFatalError`; повтор той же команды завершился с предупреждением,
без отключения проверок. Это не устраняет уязвимость. Обновление зависимостей
и повторные проверки перед новым публичным развёртыванием требуют отдельной
задачи команды; версии пакетов в этой части не изменены.

## Применение в Neon

1. Сначала создайте QA-ветку от рабочей базы в Neon. Убедитесь, что восстановление
   рабочей базы доступно; сохраните резервную копию перед производственным запуском.
2. Скопируйте **прямую**, не pooled, строку подключения QA-ветки в приватный файл
   вне репозитория. Название переменной — `DATABASE_URL_UNPOOLED` либо
   `DIRECT_DATABASE_URL`. Не отправляйте строку в чат и не включайте файл в коммит.
3. В следующей команде замените путь и хост на данные **QA-ветки**. Скрипт требует
   точного совпадения хоста и флага `--apply`; обычный `DATABASE_URL` не используется.

```powershell
node --env-file="C:/private/studyhub-qa.env" scripts/migrate-lesson-archive.mjs --host "<прямой-хост-QA>" --apply
```

4. Повторите команду: ожидается сообщение, что миграция уже применена. Проверьте
   число строк в занятиях, заданиях, работах, файлах, оценках и посещаемости до и
   после — они должны совпадать. В QA проверьте скрытие практики и её СРСП,
   сохранение оценок в журнале и возможность занять освободившуюся аудиторию.
5. После проверки примените тот же скрипт к рабочей базе, явно указав её отдельный
   приватный файл и прямой хост. Затем публикуйте backend и интерфейс. Не запускайте
   повторное заполнение данных (`seed`), сброс, удаление таблиц или импорт базы:
   для этой доработки они не нужны.

```sql
SELECT key, value FROM studyhub_settings WHERE key='lesson_archive_v1';
SELECT count(*) AS lessons, count(archived_at) AS hidden FROM school_lessons;
SELECT count(*) AS assignments FROM school_assignments;
SELECT count(*) AS submissions FROM school_submissions;
SELECT count(*) AS files FROM school_files;
SELECT count(*) AS grades FROM school_grades;
SELECT count(*) AS attendance FROM school_attendance;
```

При подготовке этого пакета рабочая база Neon не изменялась. Само наличие
миграции в GitHub не означает, что она уже выполнена в облаке.

## Передача участнику 2

Для публикации API недостаточно коммита части 1. Нужны успешная проверка на QA,
доступная резервная копия и применение `lesson_archive_v1` на рабочей Neon.
Если QA-ветка и её приватный файл подключения ещё не подготовлены, готовность
рабочей схемы не подтверждена: публикацию API следует отложить.

После миграции участник 2 должен фильтровать архивные занятия при построении
расписания и расчёте занятости, запрещать новые ссылки на них понятной ошибкой API
и сохранять доступ к оценкам, посещаемости, заданиям и файлам. Нельзя просто убрать
исторические ID занятий из данных журнала: существующие фильтры прав используют
эти ID для отбора оценок. Скрытие самой практики и её СРСП относится к одной операции.

Для объяснения реализации:

- `migrateSqliteLessonArchive` добавляет столбец и индексы в одной транзакции,
  проверяет внешние ключи и записывает маркер только после успеха.
- `migratePostgresLessonArchive` делает то же структурное обновление через явную
  команду с блокировками и откатом; старт приложения его не вызывает.
- `refreshSqliteArchiveTriggers` / `refreshPostgresArchiveTriggers` меняют только
  четыре проверки: скрытые занятия освобождают слот, а новые задания и СРСП
  не могут ссылаться на скрытое занятие. Ранее созданные работы сохраняются.
- `readSqliteSnapshot` проверяет согласованность маркера со схемой;
  `importSqliteSnapshot` переносит значения архива и восстанавливает индексы
  вместе с остальными данными в рамках существующего безопасного импорта.
