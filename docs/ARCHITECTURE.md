# Как устроен StudyHUB

## Один запрос от страницы до базы

```text
Страница app/tasks/page.tsx
  → компонент TasksPage
  → fetch('/api/assignments/.../submission')
  → обработчик app/api/.../route.ts
  → проверка сессии, роли и данных
  → SQL-запрос в PostgreSQL (или локальный SQLite)
  → ответ JSON
  → обновление данных на странице
```

Next.js отвечает и за страницы, и за API. Отдельный Express-сервер не нужен.
Страницы и корневой layout — серверные компоненты. Формы, диалоги и кнопки
состояния написаны как клиентские React-компоненты с `'use client'`.

Каждый файл `app/.../page.tsx` подключает свой компонент. Общая оболочка
`studyhub-app.tsx` рисует меню и шапку, а содержимое получает через `children`.
Она больше не импортирует все кабинеты сразу. Переходы используют `next/link`.

## Где что изменять

- Новый экран: маршрут в `app/` и компонент в `components/studyhub/`.
- Новое поле или тип ответа: `lib/studyhub/api-contract.ts`.
- Проверка прав и значений: `lib/studyhub/policy.mjs`.
- HTTP-запросы и сообщения об ошибках: `lib/studyhub/auth-http.ts`.
- Аккаунты, справочники, расписание: `lib/studyhub/auth-store.mjs`.
- Задания, работы, оценки, материалы: `lib/studyhub/learning-store.mjs`.
- Таблицы и индексы: `database/schema.mjs`; преобразование схемы для PostgreSQL,
  подключение и транзакции: `database/connection.mjs`.
- Учебные примеры: `database/seeds/`, затем локальное заполнение SQLite
  и при необходимости импорт в PostgreSQL.
- Цвета: `app/styles/tokens.css`; общие правила: `app/styles/styles.css`.

## Авторизация и роли

Пароль хранится как scrypt-хеш. После входа сервер создаёт сессию в БД,
а браузер получает случайный идентификатор в HttpOnly-cookie.
У каждого запроса проверяется текущий пользователь. Студент получает
свои работы и оценки, преподаватель — только назначенные ему группы и предметы.

Изменения дополнительно требуют правильный Origin и CSRF-токен.
Поле `version` защищает от случайного перезаписывания записи, которую уже
изменил другой пользователь: сервер возвращает 409, и список нужно обновить.

Выбор роли в окне «Аккаунт» вызывает `POST /api/auth/demo`. Сервер входит в один
из трёх подготовленных аккаунтов; роль произвольного пользователя не меняется.
Этот API выключен в обычном режиме и не запускается на базе обычных аккаунтов.

Окно открывается карточкой пользователя внизу боковой панели. В нём также
находятся переход в профиль и выход. При первом входе выбор учебного аккаунта
доступен в блоке «Учебный доступ». Интерфейс использует нейтральные названия,
а изоляция учебной базы по-прежнему задаётся `STUDYHUB_DEMO_MODE` на сервере.

## Данные

При заданном `DATABASE_URL` сервер подключается к PostgreSQL в Neon.
Без этой переменной локально используется отдельный SQLite-файл; на Vercel
`DATABASE_URL` обязателен. В обеих базах находятся таблицы пользователей,
групп, предметов, занятий, заданий, работ, оценок, посещаемости, материалов
и объявлений. Загруженные файлы тоже сохраняются в БД: `bytea` в PostgreSQL,
`BLOB` в SQLite. Схема приложения задана в `database/schema.mjs`, адаптация
к PostgreSQL — в `database/connection.mjs`. Файл `database/design/postgresql.sql`
содержит исторический проект ER-схемы и не выполняется приложением.
Исходники содержат только схему и код заполнения вымышленными примерами.
Браузер не импортирует примеры и не хранит учебные данные в localStorage.

Единый журнал хранит числовой балл 0–100 либо отдельный статус:
`not_required` (н.п.), `absent` (Н), `unmarked` (пустая ячейка).
Только числовые баллы участвуют в среднем, включая ноль.
Историческая таблица посещаемости сохранена для совместимости API;
новый интерфейс работает с отметками журнала.

Язык и тема находятся в `components/studyhub/preferences.tsx`, словарь —
в `lib/studyhub/i18n.ts`. Cookie позволяют серверу сразу отдать нужный язык
и тему без вспышки другого оформления; localStorage хранит копию настройки.
Переводится интерфейс, а имена пользователей, групп и тексты заданий
остаются такими, какими их сохранили в базе.

Большой учебный набор готовится в SQLite из `database/seeds/campus-data.mjs`.
Он дополняет сохранённые записи до учебных групп с реалистичной численностью
и строит расписание по будням в фиксированных временных слотах. В базе хранится
отметка применённого набора: повторный запуск не должен создавать дубликаты
или сбрасывать сделанные через интерфейс изменения. Сохранённый SQLite-набор
переносится в пустую PostgreSQL-базу командой
`npm run db:import -- --source "<абсолютный путь к auth.sqlite>"`.
Она применяет актуальную схему и сохраняет идентификаторы, хеши паролей
и файлы; сессии не переносятся. После перехода на Neon
SQLite остаётся резервной копией и автоматически не синхронизируется.

Используются внешние ключи, индексы и транзакции. SQLite работает в режиме WAL,
а PostgreSQL — через пул соединений. Результаты запросов учебных данных
ограничиваются текущей ролью до отправки в браузер.

## Что изменено для скорости

- Кабинеты подключаются своими маршрутами, а не одним общим импортом.
- Провайдер черновиков преподавателя отделён от тяжёлого файла его страниц.
- После изменения запрашивается только `/api/bootstrap`, без повторного запроса сессии.
- Форматтеры дат создаются один раз и повторно используются в таблицах.
- Пул PostgreSQL повторно используется внутри процесса; данные сессии и
  актуальная роль читаются одним запросом без кэширования прав пользователя.
- Удалены неиспользуемые Tailwind и его CSS-загрузчик.
- Добавлены состояние загрузки, страница ошибки и понятная 404.

Это изменения в устройстве приложения; точное ускорение в процентах не измерялось.
Для защиты проекта полезно пройти путь одного запроса и объяснить, зачем
нужны серверная проверка роли и отдельная база.
