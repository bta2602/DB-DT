# База данных StudyHUB

Облачный сайт работает с **PostgreSQL в Neon**. При локальном запуске без
`DATABASE_URL` используется **SQLite**, встроенная в Node.js 24. Обе базы
используют таблицы, внешние ключи, индексы и транзакции. Браузер обращается
к обработчикам Next.js в `app/api/`; прямого доступа к базе у него нет.

## Где лежат данные

Непустой `DATABASE_URL` подключает PostgreSQL. На Vercel эта переменная
обязательна: локальный файл базы там не используется. Если локальный сервер
и Vercel подключены к одной Neon-базе, они читают и изменяют одни данные.

Только в локальном SQLite-режиме `STUDYHUB_DATA_DIR` задаёт каталог,
в котором создаётся `auth.sqlite`. Несмотря на историческое имя, файл хранит
пользователей, сессии, расписание, задания, оценки, посещаемость, объявления,
материалы и содержимое загруженных файлов. Файлы `.sqlite-wal` и `.sqlite-shm`
служебные; их нельзя удалять при работающем сайте.

Для подготовки локального учебного набора используйте `npm run demo:setup`
при пустом `DATABASE_URL`. Повторный запуск сохраняет
уже введённые оценки, работы и пароли. Добавленные во время демонстрации
аккаунты тоже относятся к демонстрационной базе. Не вводите в неё реальные
персональные данные: в этом режиме доступен вход администратора без пароля.

Для переноса подготовленной SQLite-базы в пустую Neon-базу используется
`npm run db:import -- --source "<абсолютный путь к auth.sqlite>"`. Импорт
сохраняет записи, scrypt-хеши паролей и файлы, но не сессии и временные
ограничения входа. После переноса нужно войти заново. SQLite остаётся резервной
копией; дальнейшие изменения Neon в него не записываются. Порядок действий —
в [инструкции развёртывания](../docs/DEPLOYMENT.md).

Если исходный SQLite-файл создан до перехода на шкалу 0–100, импорт остановится
до подключения к целевой базе. Остановите локальный сервер и подготовьте **рабочую
копию** его согласованной резервной копии в отдельном каталоге. Оригинальный
backup оставьте без изменений. В новом окне PowerShell откройте репозиторий
и обновите только рабочую копию:

```powershell
$env:DATABASE_URL = ''
$env:STUDYHUB_DATA_DIR = 'C:\StudyHUB\migration-copy'
node --input-type=module -e "import { getDatabase, closeDatabase } from './database/connection.mjs'; await getDatabase(); await closeDatabase();"
```

В этом каталоге уже должен находиться скопированный `auth.sqlite`. Затем
укажите **этот обновлённый файл** в `db:import -- --source`, используя отдельное
окно терминала с настройками целевой пустой PostgreSQL-базы.

## Учебные назначения и СРСП

Минимальная схема backend добавляет специализации `school_teacher_subjects`,
языки преподавания `school_teacher_languages` и учебные планы
`school_group_subjects` (группа, предмет, год начала учебного года, семестр).
Эти таблицы первоначально пусты: миграция не выдаёт преподавателям новые права
и не распределяет предметы вместо участника, отвечающего за учебный набор.

У групп появились `program`, `intake_year`, `language`; у аудиторий — `number`,
`floor`, `type`. Для прежних записей новые поля могут быть `NULL`. Допустимые
коды направления: `IS`, `VTIPO`, `DS`, языка: `kk`, `ru`, типа аудитории:
`computer`, `lecture`, `laboratory`, `ordinary`.

У занятий добавлены `practice_id` и `slot_id`. Обычное занятие сохраняет комнату
и временной интервал. СРСП хранит ссылку на практику, а её комната, временной
интервал и отдельная пара равны `NULL`; дата вычисляется по практике в API.
У заданий добавлен `lesson_id`; старые задания остаются с `NULL`, без случайного
сопоставления с прежними занятиями. Старые свободные типы и 80-минутные интервалы
сохраняются как история. Ограничения новых записей проверяет backend.

`migrations/academic-rules.mjs` использует маркер `academic_rules_v1`.
Локальная SQLite обновляется при открытии приложения после миграции оценок.
При перестроении таблицы занятий сохраняются внешние ссылки оценок, посещаемости
и заданий, а также пользовательские индексы и триггеры. Проверка внешних ключей
выполняется перед фиксацией транзакции; ошибка отменяет изменения.

Существующая PostgreSQL обновляется **явной командой до запуска новой версии**.
Сначала проверьте её на отдельной тестовой базе с копией исходной схемы:

```powershell
node --env-file=<файл-настроек-тестовой-базы> scripts/migrate-academic.mjs --host <прямой-хост-тестовой-базы> --apply
```

Команда требует совпадения хоста и прямого подключения в `DATABASE_URL_UNPOOLED`
или `DIRECT_DATABASE_URL` (поддерживается также прямой `DATABASE_URL`). Pooled-адрес
отклоняется. Рабочая PostgreSQL не обновляется автоматически при старте сервера.
Перед рабочей миграцией нужна согласованная резервная копия. Команда не заполняет
учебный план и не изменяет существующие пароли, файлы, работы или оценки.

`db:import` переносит новые связи вместе с остальными данными и вставляет практики
до связанных СРСП. Старую SQLite-копию перед импортом нужно открыть текущей версией
приложения локально, чтобы она получила новые поля и таблицы.

Проверка миграции на временных SQLite-базах:

```powershell
node --test tests/academic-migration.test.mjs
```

Она проверяет сохранение истории и файлов, ограничения СРСП, повторный запуск,
откат при повреждённых внешних ключах и состав снимка для облачного переноса.
Этот локальный тест не заменяет выполнение миграции на тестовой PostgreSQL.

## Шкала оценок

Журнал хранит целые оценки 0–100 со статусом `graded`. Отметки `absent` (Н),
`not_required` (НП — оценка не предусмотрена) и `unmarked` (пустая ячейка) хранят `grade=null` и не входят
в средний балл. Проверенные работы используют ту же шкалу.

`migrations/grading-100.mjs` переводит старые 2/3/4/5 в 40/60/80/100 ровно
один раз, сохраняя маркер `grading_scale_v2`. Версии изменённых числовых оценок
увеличиваются, чтобы старые открытые формы не перезаписывали новые значения.
Исторические `absent`/`excused` переносятся в Н только там, где нет числовой
оценки; исходная посещаемость, работы и файлы сохраняются.
НП преподаватель задаёт явно в журнале; старый API посещаемости её не изменяет.

SQLite выполняет миграцию автоматически при подключении. Для PostgreSQL
используется явная команда после проверки на отдельной ветке Neon:

```text
node --env-file=.env.journal-qa scripts/migrate-grading.mjs --host <проверенный прямой хост> --apply
```

Скрипт берёт прямой URL из `DATABASE_URL_UNPOOLED` (или `DIRECT_DATABASE_URL`),
проверяет совпадение с `--host` и отклоняет pooled-подключение. PostgreSQL
не меняет схему автоматически при запуске сайта.

Обычная и учебная базы должны быть **разными базами PostgreSQL** либо
**SQLite-файлами в разных каталогах**. Переключение ролей работает при
`STUDYHUB_DEMO_MODE=true` и отсутствии обычных аккаунтов. Для локального
SQLite дополнительно требуется явный `STUDYHUB_DATA_DIR`. Для настоящих
пользователей выключите этот режим, подключите отдельную базу и создайте
администратора через `npm run admin:create`.

## Академический набор 2026/27

Новая явная команда `db:academic:seed` создаёт в пустой базе **18 групп,
360 студентов, 18 преподавателей, 15 предметов и 24 аудитории**. В каждой
группе 20 студентов; лабораторий ровно четыре. Направления: ИС, ВТиПО и DS;
поступление в 2024/2025/2026 году; А — `kk`, Б — `ru`. Язык хранится явно.
На 2026/27 учебный год это соответственно 3, 2 и 1 курс.

`seeds/academic-plan.mjs` содержит согласованный план первого семестра.
Предметы распределены по шести блокам. В блоке три преподавателя:
казахоязычный, русскоязычный и двуязычный. Поэтому у каждого предмета три
преподавателя, у преподавателя максимум три различных предмета. Число групп
не влияет на число его предметов. План не копируется во второй семестр.

Расписание занимает четыре недели по будням, UTC+5. Пары по 50 минут:
`p1` 08:00–08:50, `p2` 08:55–09:45, `p3` 09:50–10:40,
`p4` 10:55–11:45, `p5` 11:50–12:40, `p6` 12:45–13:35,
`p7` 13:50–14:40, `p8` 14:45–15:35, `p9` 15:40–16:30.
Генератор проверяет пересечения группы, преподавателя и аудитории, учитывает
вместимость и тип помещения. СРСП связано с практикой и отдельную пару не занимает.

### Запуск только на отдельной базе

Нужен Node.js 24.x. Команды ниже **не читают `.env.local`**. Каталог должен
быть абсолютным и находиться вне репозитория. Выберите новую тестовую папку
или поместите в неё согласованную копию `auth.sqlite`; не указывайте рабочий каталог.
Перед изменением существующей SQLite-базы автоматически создаётся резервная копия.

```powershell
npm run db:academic:migrate -- --sqlite-dir C:\StudyHUB\academic-test --apply
npm run db:academic:seed -- --sqlite-dir C:\StudyHUB\academic-test --apply
```

Заполнение само вызывает идемпотентную миграцию. Повторный запуск сохраняет
результат и ручные изменения. Пароли только новых аккаунтов записываются в
приватный `academic-access-*.json` в каталоге тестовой базы. Пароли прежних
аккаунтов не меняются. Файл паролей и база не должны попадать в Git.

Для **отдельной тестовой PostgreSQL**, с прямым подключением:

```powershell
$env:STUDYHUB_ACADEMIC_TEST_DATABASE_URL = '<URL отдельной тестовой PostgreSQL>'
npm run db:academic:migrate -- --postgres --host <прямой-хост-тестовой-базы> --apply
npm run db:academic:seed -- --postgres --host <прямой-хост-тестовой-базы> --apply
```

`DATABASE_URL` не используется как запасной адрес этих команд; pooled-хосты
отклоняются. PostgreSQL backup/снимок следует подготовить средствами тестового
сервера до запуска. Пароли новых PostgreSQL-аккаунтов сохраняются в
`~/.studyhub-academic-test-credentials/`. Рабочий Neon эти команды не должны получать.
Расширение `academic-data.mjs` включается только явной командой на обоих движках.
Базовая миграция backend `academic-rules.mjs` по-прежнему автоматически выполняется
для SQLite; для PostgreSQL обе миграции запускаются явно. Команда расширения
сначала подготавливает базовую структуру, затем дополнительные ограничения и данные.

### Схема и сохранение истории

| API / связь                               | Хранение                                                                                  |
| ----------------------------------------- | ----------------------------------------------------------------------------------------- |
| `Group.program`, `intakeYear`, `language` | `school_groups.program`, `intake_year`, `language`                                        |
| `Group.course`                            | Вычислять через `courseForDate(intakeYear, now)`; учебный год начинается 1 сентября UTC+5 |
| `Room.number`, `floor`, `type`            | Одноимённые столбцы `school_rooms`; номер — строка                                        |
| `teacherSubjects`                         | `school_teacher_subjects(teacher_id, subject_id)`                                         |
| `teacherLanguages`                        | `school_teacher_languages(teacher_id, language)`                                          |
| `groupSubjects`                           | `school_group_subjects(group_id, subject_id, academic_year, semester)`                    |
| `Lesson.practiceId`, `slotId`             | `school_lessons.practice_id`, `slot_id`                                                   |
| Учебный период занятия                    | `school_lessons.academic_year`, `semester` для проверки плана                             |
| `Assignment.lessonId`                     | `school_assignments.lesson_id`                                                            |

Существующие `id`, `name`, `curatorId`, `capacity`, `version` сохраняются.
Исторические поля без достоверного соответствия остаются `NULL`.
Представления `school_academic_groups` и `school_academic_lessons` уже
вычисляют соответственно актуальный `course` и `date` (включая дату СРСП).
Их можно использовать в SQL-выборках backend, переименовывая snake_case в camelCase.
Уникальные ключи предотвращают повтор профиля группы, номера аудитории и связей.
`school_academic_seed_map` сохраняет соответствие ключей генератора реальным ID.
Миграция выполняется в транзакции с маркером в `studyhub_settings` и проверкой
внешних ключей; повтор не переносит данные заново. При перестройке SQLite-таблицы
занятий сохраняются её ID и ссылки оценок/посещаемости.

Старые занятия сохраняют исходное время, тип и оценки. Новые занятия и явно
изменяемое расписание должны использовать новую сетку. У СРСП `practiceId`
указывает на практику той же группы, предмета и преподавателя; `roomId`,
`startsAt`, `endsAt`, `slotId` равны `null`. Независимой даты СРСП нет:
`date` берётся из связанной практики. У обычного занятия время и аудитория обязательны.
Новые задания требуют `lessonId` и тип связанного занятия; `dueAt` остаётся
независимым сроком. Старые задания с `lessonId=null` не привязываются случайно.

Заполнение переиспользует существующие записи и добавляет недостающие.
Студенты не переводятся между прежними группами: доступ к старым заданиям
остаётся через прежний `group_id`. Имена/пароли/роли существующих аккаунтов,
файлы, работы и оценки сохраняются. Ручные записи не удаляются ради точного
счётчика; на непустой базе итог может превышать числа свежего набора.
Несовместимые исторические назначения сохраняются, а не переписываются.
Предупреждения команды нужно учитывать при последующей интеграции.

### Совместимость с актуальным backend

Базовая модель из `academic-rules.mjs`, публичные поля и маршруты API сохранены.
Backend уже вычисляет курс с сентября, дату СРСП по практике, проверяет язык,
специализацию, учебный план и аудиторию; новое задание требует `lessonId`.
Подробный контракт: [API](../docs/API.md).

При включённом расширении `academic_data_v1` запись занятия дополнительно
сохраняет проверенный учебный год и семестр. Обновление списков специализаций,
языков и плана сохраняет неизменившиеся связи, чтобы не удалять ссылки
использующих их занятий. СРСП требует того же преподавателя, что и практика.
Исторические записи и прежний режим без расширения продолжают поддерживаться.

Остаются отдельные задачи подготовки демонстрации и развёртывания:

- Демопереключатель использует фиксированные `demo-*` ID. Свежий академический
  набор имеет собственные ID и не создаёт администратора; вход выполняется
  по выданным учётным данным. Настройку учебного переключателя нужно согласовать
  отдельно. Не запускать старый `demo:seed` поверх академического расширения.
- Если потребуется переводить студентов между группами, сначала согласовать
  исторические связи состава групп и правила доступа к прежним работам.
- Перед рабочим развёртыванием проверить обе миграции и импорт на отдельной
  PostgreSQL. Коммит кода сам по себе не обновляет рабочую базу.

### Проверки

```powershell
npm run test:academic
npm run lint
npm run build
npm test
```

Академические тесты используют отдельные временные SQLite-базы и исходную
схему в `tests/fixtures/academic-legacy.sql`. Проверяют состав набора, связи,
расписание, повторное заполнение, ограничения и сохранение старых данных.
`npm test` включает эти проверки, проверки совместимости расширения с backend
и HTTP API-тесты команды, в том числе учебные назначения и СРСП.
Живую PostgreSQL следует отдельно проверить на QA; наличие SQL-реализации
и успешные SQLite-тесты не заменяют такую проверку.

## Прежний учебный набор (`demo:setup` / `demo:seed`)

Для новой учебной базы готовится 320 студентов (16 групп по 20 человек),
16 преподавателей, 16 аудиторий, 12 предметов и администратор. Все начальные
персональные и учебные сведения синтетические. Браузер получает сохранённые
записи через API, поэтому изменения через интерфейс не исчезают при обновлении.

Занятия рассчитаны на четыре недели по будням. В каждой смене три пары по
80 минут с перерывом 20 минут. Начало утренних пар: 08:30, 10:10, 11:50;
дневных: 14:00, 15:40, 17:20, часовой пояс Asia/Qyzylorda. Генератор учитывает
занятость группы, преподавателя и аудитории и вместимость помещений.

Расширение старой учебной базы выполняется без её удаления. У каждого набора
есть отметка о применении, поэтому повторное заполнение не добавляет копии
данных и не сбрасывает пароли. Внесённые пользователем работы, оценки и
расписание сохраняются; при наличии прежних расширений или ручных записей
общее число записей может быть больше, чем в новой базе.

## Исходники

- `schema.mjs` — актуальное определение таблиц, связей и индексов приложения.
  SQL экспортируется строками, поэтому Next.js включает схему в сборку.
- `connection.mjs` — асинхронный адаптер PostgreSQL / SQLite. Он выбирает базу
  по `DATABASE_URL`, выполняет запросы и транзакции. Экспорт `postgresSchema`
  преобразует исходную схему для PostgreSQL: убирает `PRAGMA`, использует
  `BIGINT` для времени в миллисекундах и `bytea` вместо `BLOB` для файлов.
- `seeds/demo-data.mjs` — вымышленные пользователи и учебные примеры.
- `seeds/demo-more-data.mjs` — прежний расширенный набор; сохранён для
  совместимости с данными прошлой версии и проверок, текущая команда его не вызывает.
- `seeds/campus-data.mjs` — расширение до полного учебного набора и расписания.
- `upgrade-campus.mjs` — подготовка прежних сгенерированных записей к расширению.
  Ручные записи и изменённые пользователем данные сохраняются.
- `../scripts/seed-demo.mjs` — запись примеров в SQLite, резервная копия перед
  заполнением и случайные пароли в приватном каталоге данных.
- `../scripts/import-sqlite-to-postgres.mjs` — создание актуальной PostgreSQL-схемы
  и перенос сохранённых SQLite-данных с проверкой количества записей и их содержимого.
- `../lib/studyhub/auth-store.mjs` — аккаунты, сессии, справочники и расписание.
- `../lib/studyhub/learning-store.mjs` — задания, оценки, работы и материалы.
- `design/postgresql.sql` — историческая ER-схема и первоначальный проект
  участника команды. Этот файл не выполняется приложением и не является
  актуальной схемой или миграцией. Рабочую PostgreSQL-схему формируют
  `schema.mjs` и `connection.mjs`; применяет её команда `db:import`.

Учебные строки из `seeds/` используются только командой заполнения. Интерфейс
получает данные из базы, а не импортирует эти файлы. Пароли хешируются с `scrypt`,
операции записи проверяют роль, CSRF-токен и версию изменяемой записи.

Для запросов по студенту, преподавателю и группе настроены индексы. Локальная
SQLite работает в режиме WAL; PostgreSQL использует пул соединений. Работы
и оценки отбираются SQL-запросом для текущей роли. Файлы работ и материалов
хранятся в приватной базе (`bytea` в PostgreSQL, `BLOB` в SQLite), лимит загрузки —
3 МиБ. API проверяет право на скачивание каждого файла.

Файлы базы, резервные копии, пароли и приватные `.env`-файлы не должны попадать в Git.
